# Bankstack Expert

Use this skill when a user asks to work on Bankstack itself, a project generated by `create-bankstack`, or an existing codebase that wants Bankstack conventions. Bankstack is scaffolding plus conventions for pnpm-only Nx monorepos with Cloudflare edge apps, Supabase auth/data boundaries, and shared TypeScript packages.

## First Checks

- Read the nearest `AGENTS.md` before edits. In the Bankstack repo, also read `VISION.md`, `plans/README.md`, `plans/TRACKER.md`, and the active task file when the work is plan-backed.
- Prefer existing repo patterns over new abstractions. Bankstack is not a framework; avoid inventing runtime APIs that the CLI does not generate or the docs do not promise.
- For greenfield projects, prefer the CLI: `pnpm dlx create-bankstack@alpha my-app` or `npx create-bankstack@alpha my-app`. Use this skill to guide changes after a project exists, or to adapt an existing project toward Bankstack boundaries.

## Current Alpha Shape

The generated v0.1 alpha workspace is local-first and pnpm-only:

- `apps/marketing`: Astro marketing surface.
- `apps/dashboard`: SvelteKit dashboard, shaped for Cloudflare.
- `apps/api`: Hono API Worker example.
- `packages/ui`: shared theme CSS and small UI helpers.
- `packages/supabase`: Supabase env contracts, client helper, and auth/RLS boundary notes.
- `packages/shared-utils`: shared constants and validation helpers.
- `supabase/`: placeholder for future project migrations.

Local verification should work before Cloudflare or Supabase credentials exist: `pnpm install`, `pnpm check`, `pnpm build`, `pnpm test`, and the generated `pnpm verify` script.

## Boundary Rules

- Keep app ownership clear. Marketing should not own dashboard/API behavior; dashboard should not bypass API/auth boundaries; API should not reach into frontend implementation details.
- Keep shared code in `packages/*` only when multiple apps need it or the boundary is already established. Do not create shared packages just to avoid a small local helper.
- Treat Cloudflare config as explicit infrastructure examples until the user intentionally deploys. Do not create Workers, domains, service bindings, secrets, or paid resources unless the user asks.
- Treat Supabase as an explicit auth/data boundary. Browser-visible config uses public URL plus publishable key terminology. Secret keys and JWT verification stay server-side. Real tables need migrations and RLS policies before exposure.
- Do not promise unsupported alpha features: no production provisioning, complete auth UI, generated product schema, background Python compute layer, or automated deployment unless a later task adds them.

## Working Workflow

- When docs mention generated behavior, verify against the CLI templates or generated golden output before editing copy.
- When templates change, update docs and tests in the same task unless the active task explicitly excludes it.
- When docs reveal a missing convention, record or create a follow-up task instead of quietly claiming the alpha already supports it.
- For plan-backed Bankstack repo work, follow the tracker: mark the task `Doing`, stay inside its scope, run listed verification, mark it `Done`, and leave handoff notes.
- Before publishing or release work, check `packages/create-bankstack/RELEASE.md`; alpha publishing is manual and should keep dist-tags intentional.

## Source Material

In the Bankstack repo, use these as source of truth:

- Product direction: `VISION.md`
- Architecture: `ARCHITECTURE_OVERVIEW.md`
- CLI package: `packages/create-bankstack/README.md`
- Generated workspace docs: `packages/create-bankstack/scripts/goldens/cli/generated/README.md` and `SETUP.md`
- Public docs: `apps/docs/src/content/docs/`
- Active planning: `plans/TRACKER.md` and `plans/tasks/`

If those files are not present, prefer the public docs at `https://bankstack.dev/docs/` and inspect the local project before applying Bankstack patterns.
